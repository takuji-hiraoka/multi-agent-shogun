# /spec-doc-parallel — 並行作業時の設計書テンプレート

## 1. Overview — スキルの目的と適用範囲

並行進行中の複数Issue/cmd で、**同一ファイルを両方のPRが編集する状況**（共有ファイル衝突リスク）に対して、
設計書に「衝突リスク定量化・マージ順序・確定形ルール・並行作業注意点」の4セクションを自動挿入するテンプレートスキル。

軍師がこのスキルを呼び出すと、各セクションの**空雛形**がコピペ可能な形式で提供される。
実際の内容（ファイル名・リスク判定・ルール内容）は軍師が埋める。

**背景**: cmd_205/206/208 の並行作業で毎回手作りしていたセクションをスキル化したもの。
3 cmd 並行で得た「State union の確定形ルール必須」「rebase衝突箇所の最小ファイル化」等の知見を体系化。

## 2. When to Use（発火条件・非発火条件）

**発火条件（いずれかに該当）**:
- 並行進行中の cmd / Issue / PR が **2件以上** ある
- 共有ファイル（両方が編集予定）が **2個以上** ある
- 軍師が「セクション10/11 相当の並行作業注意点」を設計書に書こうとしている
- 後発PR担当の足軽が rebase で迷う恐れがある
- 「並行設計」「並行作業注意点」「rebase戦略」「設計書テンプレート」「複数Issue仕様」「後発PR rebase」「確定形ルール」と言われたとき

**Do NOT use for（非発火条件）**:
- 単一Issue / 単独PR で他PRと共有ファイルなし
- 実装作業（vm.ts 等の編集）— 本スキルは設計書テンプレ専用
- PR作成・マージ作業（レビューや実装の話）
- ファイル数1個 + マージ順序が明確（衝突リスク低）

## 3. Output Template（軍師が設計書末尾にコピペする雛形）

以下の Markdown を設計書の適切なセクション（例: セクション10または11）に貼り付け、
`<placeholder>` 箇所を実際の値で埋める。

---

### N.1 共有ファイル衝突リスク評価

並行進行中の cmd を以下の表で衝突リスク評価する。

| ファイル | `<cmd_X>` の編集 | `<cmd_Y>` の編集 | 衝突リスク | 対処 |
|---------|---------------|---------------|------------|------|
| `<path/to/shared1.ts>` | `<append: 型追加>` | `<append: 型追加>` | **高** | 確定形ルール（セクションN.3）適用 |
| `<path/to/shared2.ts>` | `<関数追加>` | `<別関数追加>` | **低** | append-only → 自動マージ可 |
| `<path/to/shared3.html>` | `<要素追加>` | `<要素追加>` | **中** | DOM順序ルール（セクションN.3）適用 |

**判定基準**:
- **低**: append-only / クラス名重複なし → 自動マージ可
- **中**: 同関数/同セクション編集 → 手動マージ必要
- **高**: 同行/同型union編集 → 確定形ルール必須

---

### N.2 マージ順序の推奨

```
① 先行PR (<cmd_X>) を先にマージ（依存関係 or レビュー進度で選定）
② 後発ブランチ (<cmd_Y>) で `git rebase main`
③ 衝突解消（セクションN.3 の確定形ルール適用）
④ <プロジェクト固有のバリデーション: npm run validate 等> で全テスト通過確認
⑤ 後発PR レビュー
```

**先行PR選定の根拠**: `<例: cmd_X は独立機能で他に依存なし、先行マージが安全>`

---

### N.3 後発の rebase 戦略・確定形ルール

後発ブランチが `git rebase main`（先行PRマージ後）したときに発生する衝突に備え、
以下の「確定形ルール」を機械的に適用できる形で定義する。

#### N.3.1 型 union の確定形ルール（該当ファイル: `<path/to/types.ts>` 等）

```typescript
// 確定形 — 後発は必ずこの順序で追記すること
type <TypeName> =
  | '<existing_value_a>'    // 既存
  | '<existing_value_b>'    // 既存
  | '<cmd_X_addition>'      // 先行マージ（cmd_X）
  | '<cmd_Y_addition>';     // 後発マージ（cmd_Y）
```

#### N.3.2 DOM 配置順ルール（該当ファイル: `<path/to/index.html>` 等）

```html
<!-- 確定形 — 後発は必ずこの順序で要素を追加 -->
<section id="<existing-section>"><!-- 既存 --></section>
<section id="<cmd_X-section>"><!-- 先行マージ（cmd_X） --></section>
<section id="<cmd_Y-section>"><!-- 後発マージ（cmd_Y） --></section>
```

#### N.3.3 dispatch / handler 順序ルール（該当ファイル: `<path/to/background.ts>` 等）

```typescript
// 確定形 — メッセージ dispatch / case の順序を固定
switch (message.type) {
  case '<existing_action>':  // 既存
    break;
  case '<cmd_X_action>':     // 先行マージ（cmd_X）
    break;
  case '<cmd_Y_action>':     // 後発マージ（cmd_Y）
    break;
}
```

---

### N.4 並行作業注意点（後発PR担当足軽向けチェックリスト）

後発ブランチ (`<cmd_Y>`) の足軽は以下を **rebase・テスト・PR作成前** に確認すること:

- [ ] `git fetch origin && git rebase origin/main` を先行PRマージ後に実行した
- [ ] セクションN.3 の確定形ルール通りに衝突を解消した
- [ ] `<バリデーションコマンド>` が PASS した（SKIP=FAIL ルール適用）
- [ ] 既存テスト件数が変動していない（削除・スキップなし）
- [ ] 先行PRで追加された機能との統合テストを1ケース以上実行した
- [ ] PR本文に「先行PR #<先行PR番号> マージ後に rebase 済み」と明記した

## 4. Parameter Detection（自動収集できる項目）

スキル呼び出し時に自動収集・確認できる項目:

**自動収集（引数または git コマンドから）**:
- `parent_cmd_id`: 引数から（例: `cmd_209`）
- 現在のworktreeブランチ名: `git branch --show-current`
- 並行中の他cmd_id一覧: `ls queue/tasks/cmd_*.yaml` で status=in_progress を抽出
- 共有ファイル候補: `git diff origin/main --name-only` を並行ブランチ間で比較

**手動入力が必要な項目**:
- 各ファイルの「編集内容の具体的意図」（append / replace / delete等）
- 先行PR選定の判断根拠
- 確定形ルールの具体的な型名・値

## 6. Guidelines（軍師が判断する3原則）

1. **発火判定**: 共有ファイル ≥ 2個 + 並行PR ≥ 2件で適用必須。
   どちらか一方でも欠けていれば原則不要（衝突リスクが線形でなく急増するため）。

2. **確定形ルールの記述位置**: 後発PR担当の足軽が「このファイルのこの型を、この順序で追記する」と
   機械的に従えるレベルまで具体化する。抽象的な指示（「適切に処理せよ」）は禁止。

3. **旧版設計書の保全**: 仕様変更でセクションを書き直す場合、旧版は git history に保全し、
   設計書本体を改訂する（subtask_205a_rev パターン）。並行作業注意点も同様に改訂追従すること。

**例外（スキル不要）**:
- 単一ファイル変更 / マージ順序が自明な場合（衝突リスク低）
- 並行Issueが存在するが編集ファイルに重複がない場合
